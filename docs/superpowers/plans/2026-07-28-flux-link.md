# FLUX link Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make FLUX's DRAG knob bipolar. Right of centre it keeps pulling the delay time (and bending pitch, as built). Left of centre the clock never moves and the neighbour's rhythm decides which repeats sound.

**Architecture:** No new DSP object and no new line. The step accumulator DRAG already runs becomes the repeat clock for the left half; a two-entry skip pattern derived from the neighbour's raw gaps drives a ramped gain on the echo return, before `_mix_lin`.

**Tech Stack:** C++17, doctest, CMake + Ninja + clang (desktop), VCV Rack SDK (`host/vcv`), Python (the panel contract guard).

**Spec:** `docs/superpowers/specs/2026-07-28-flux-link-design.md`
**Amends:** `docs/superpowers/specs/2026-07-28-flux-rhythm-drag-design.md` — that mechanism survives as the positive half.

## Global Constraints

- Namespace `spky` for engine code, `spkyvcv` for VCV host code.
- **LINK at 0 (centre) must be bit-identical** to FLUX without this feature. Every pre-existing test stays green unmodified apart from the mechanical `set_drag` → `set_link` rename.

- `apply_drag()` remains the single writer of `_dt_target`.
- The thinning path reads `rv.gap[]` **directly** and must NOT call `derive_intervals` — an even pattern is a failure for DRAG and a *result* for thinning (spec §2.1).
- The gate sits on the **echo return, before `_mix_lin`**, never in the feedback path.
- `res/gen_panel.py`'s `Ctl` list order defines param ids: rename in place, never insert. `PART_STRIDE` stays 23.

### Task 2: The thinning mechanism

**Files:**
- Modify: `engine/fx/drag.h`, `engine/fx/flux.h`, `engine/fx/flux.cpp`, `tests/test_flux.cpp`, `host/vcv/README.md`

**Interfaces:**
- Consumes: `Flux::set_link` (Task 1), `RhythmView` (`engine/mod/rhythm_view.h`), the existing `_drag_phase` / `_drag_step_len` accumulator
- Produces:
  - `spky::link_tuning::{kMaxSkip, kGateRampS}`
  - `float Flux::gate_for_test() const`, `int Flux::thin_n_for_test(int i) const`

**How it works.** The delay time never leaves its RATE rung. The neighbour's raw gaps are rounded to whole repeats — `n0`, `n1` — and the pattern is "one repeat sounds, `n-1` are ducked, swap interval, repeat". The accumulator DRAG already runs fires at each repeat boundary and advances that pattern; a 3 ms one-pole ramp carries the gain between sounding and ducked so the gate does not click.

```cpp
// The neighbour's gaps, in whole repeats of the CURRENT ladder time. Rounded,
// not truncated: a gap of 3.6 repeats is heard as 4, not 3.
void Flux::update_thin_pattern() {
    const float rep = _delay_time * _sr;
    for (int i = 0; i < 2; ++i) {
        int n = 1;
        if (rep > 0.f)
            n = static_cast<int>(static_cast<float>(_rhy_gap[i]) / rep + 0.5f);
        if (n < 1) n = 1;                                  // shorter than one
        if (n > link_tuning::kMaxSkip) n = link_tuning::kMaxSkip;
        _thin_n[i] = n;
    }
}

// One repeat further into the pattern. The FIRST repeat of each interval
// sounds and the rest are ducked, which puts the audible event on the
// neighbour's onset rather than before it.
void Flux::advance_gate() {
    ++_thin_count;
    _gate_target = (_thin_count == 1) ? 1.f : (1.f - _thin);
    if (_thin_count >= _thin_n[_thin_i]) {
        _thin_count = 0;
        _thin_i ^= 1;
    }
}
```

Rewrite `apply_drag`'s inert branch — it now has to arm the repeat clock for the other half, and must NOT reset the phase while thinning is running, or every knob movement would restart the pattern:

```cpp
void Flux::apply_drag() {
    const bool thinning = (_thin > 0.f && _rhy_valid);
    if (_drag <= 0.f || !_drag_active) {
        _dt_target = _delay_time;
        // Thinning needs the same accumulator, stepping on the LADDER time --
        // the clock never moves on that half, which is the entire point.
        _drag_step_len = thinning ? _delay_time * _sr : 0.f;
        if (!thinning) { _drag_phase = 0.f; _gate_target = 1.f; }
        return;
    }
    const float target = static_cast<float>(_drag_iv[_drag_i]) / _sr;
    _dt_target = std::pow(_delay_time, 1.f - _drag) * std::pow(target, _drag);
    _drag_step_len = _dt_target * _sr;
}
```

```cpp
    // The gate keeps running after thinning disengages so the gain ramps back
    // to unity instead of stepping; the snap is what lets the branch switch
    // itself off again and restore the bit-exact path (fonepole never quite
    // arrives -- the same reason _stage_current carries a snap above).
    if (thinning || _gate != 1.f) {
        daisysp::fonepole(_gate, _gate_target, _gate_coef);
        if (std::fabs(_gate - 1.f) < 1e-6f) _gate = 1.f;
        el *= _gate;
        er *= _gate;
    }
    l += el * _mix_lin;
    r += er * _mix_lin;
```

## Notes for whoever executes this

**The one thing that could silently go wrong.** `apply_drag` is still the single writer of `_dt_target`, and Task 2 adds a second consumer of `_drag_step_len` without adding a second writer. If a later edit gives thinning its own accumulator, the two will drift apart and the pattern will stop lining up with the repeats it is supposed to gate. The mutual exclusion is load-bearing: `_drag` and `_thin` come from opposite signs of one knob and can never both be positive.

**Why there is no bench task.** No new `BbdLine`, no new memory, and the per-sample addition is one predicated compare plus — only while thinning — one `fonepole` and two multiplies. The previous branch's measurements stand.
